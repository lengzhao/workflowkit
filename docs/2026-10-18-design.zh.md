## 1. 包结构

```
workflowkit/                     # 核心：注册、解析、调度、模板、自描述
├── doc.go                       # 定位与不变量
├── registry.go                  # Register / ListTypes / Describe + 构造函数规范化
├── describe.go                  # NodeInfo / Option / schema 推导 / config 解码
├── types.go                     # Node / Ctx / Env / Output + 宿主能力接口 + Ctx 方法
├── workflow.go                  # Workflow / Step / Retry + Parse + 加载期校验
├── engine.go                    # Run：分层调度、when/retry/timeout、spill、Result
├── graph.go(在 schema.go 内)     # 依赖解析、成环检测、分层、关键路径估算
├── template.go                  # 模板渲染、dig/quote/readJSON、JSON 类型保真
├── schema.go                    # JSON Schema 校验、Schema()、图算法
└── load.go                      # Load / LoadDir / LoadDirs（目录发现）

nodes/                           # 内置节点 = 普通注册，非特权代码
├── nodes.go                     # 空导入聚合
├── script/                      # script：经 Shell 跑命令
├── tool/                        # tool：经 ToolInvoker 调工具
├── model/                       # model：单次补全 + outputSchema 校验
├── agent/                       # agent：同步委派子 Agent
└── foreach/                     # foreach：唯一的循环，也是组合节点参考实现
```

核心**不 import** `nodes/*`：`nodes/nodes.go` 是给宿主用的聚合空导入。删掉任何内置节点包，库依然可用。

## 2. 三个层次

| 层 | 内容 | 谁定义 |
|---|---|---|
| **注册** | `Register(kind, ctor, opts…)` | 节点作者（`init()`） |
| **描述** | `NodeInfo`（Config schema / Example / SubSteps） | 节点作者（Option） |
| **执行** | `Node.Run(ctx, env, c)` | 核心调度，节点只做自己的事 |

---

## 3. 注册：构造函数规范化

`Register` 接受两种形态，其余在注册时 panic（照搬 pluginkit）：

```go
func New() (N, error)
func New(cfg Q) (N, error)     // Q 是 struct；Q 与 *Q 都可，取决于构造函数签名
```

规范化流程（`registry.go:parseConstructor`）：

1. 必须是函数、非变参、返回 `(T, error)`
2. `T` 必须实现 `Node`
3. 单参时，该参数必须是 struct（或指向 struct 的指针）
4. 闭包化：`func(cfg map[string]any) (Node, error)`

**config 解码的两级严格性**：

| 位置 | 严格性 | 目的 |
|---|---|---|
| 核心的公共字段 | 已知 | 核心只认 `id/type/when/dependsOn/continueOnError/retry/timeoutSeconds`，其余全归节点 |
| 节点自己的字段 | `DisallowUnknownFields` | 拼错字段名立刻报错 |

这正是 pluginkit `build/decode.go` 的严格性，只是**下放到节点内部**——因为定义文件是扁平的，核心无法预先知道节点的字段。

## 4. 加载期校验：两遍

`Parse` 做两遍校验，目的是让"能加载期查的一律加载期报"：

**第一遍：结构（JSON Schema）**
- `description` 必填、`steps` ≥ 1、`concurrency` ≥ 0
- 每个 step：`id` 非空且唯一、`type` 是注册过的 kind
- 节点自己的字段按 `NodeInfo.Config` 校验
- `SubSteps` 声明的字段递归校验（`[]Step` 的 id/type 等）

**第二遍：构造（语义）**
- 调用一次 `CheckConfig(kind, fields)` —— 真正构造节点
- 好处：**"缺必填字段"、"枚举值非法"这类只在构造函数里的检查也变成加载期错误**，而不是等第一次 Run
- 代价：多构造一次节点（对 `script`/`tool` 这类无状态构造可忽略）

**再之后**：图校验（`dependsOn` 引用、自引用、重复、含隐式串行边的成环）、模板语法（`when` / `result`）。

> 关键收益：Agent 生成的定义能用**同一个代码路径**校验，不需要另写校验器，文档也不会与代码漂移。

## 5. 调度

```
levels()  →  Kahn 分层
     层 0: [a, b]       ← 同层并发（上限 concurrency）
     层 1: [c]          ← 依赖 a、b
```

**串行默认**：`dependsOn` 缺省 = 等前一个 step（保留旧语义）。写 `[]` 断开隐式边 → 并行起步。

**并发安全**：同层 step 的模板数据**只含更早层**的结果（`snapshot()` 在层开始时构建）；层结束后才把整层结果统一写回。所以同层并行不需要锁，`-race` 干净。

**失败传播**：同层 sibling 一定跑完（已启动的 goroutine 等 `wg.Wait()`），然后**不再开新层**。

**超时**：内层每 step（`context.WithTimeout`）。库**不设外层墙钟**——那是宿主的事，宿主可用 `wf.EstimateDuration()` 定 sizing。

**哨兵识别**：宿主可能把超时转成"看起来正常的结果"。所以执行后检查 `errorsIsDeadline(stepCtx, parent)`：step 自己的 deadline 到了就**覆盖**成超时错误，无论节点返回什么。

## 6. 模板

函数只有 3 个，条件用 text/template 内置的 `eq/ne/lt/gt/and/or/not`。

**JSON 类型保真**（三个规则，覆盖三种坑）：

| 渲染结果 | 处理 | 避免的坑 |
|---|---|---|
| 整段是 object/array | 解析成对象再传给节点 | 工具收到 JSON **字符串**而不是对象 |
| 整段单一插值且是数字 | 保持 `json.Number` | >2^53 的整数被 float64 舍入 |
| 静态 `"42"` | 仍是字符串 | 字符串被误当数字 |

`readJSON` 路径限制：只允许 `runDir` 与定义文件目录，且 `EvalSymlinks` 后再判断——**符号链接逃逸也会被拒**。

## 7. 组合节点

任何节点都能用 `Ctx.RunStep` / `Ctx.RunSteps` 跑子步骤：

```go
r, err := c.RunStep(ctx, step)          // 继承 item 上下文
rs, err := c.RunSteps(ctx, bodySteps)   // 按声明序，遇错即停（除非 continueOnError）
```

**关键**：子步骤由**核心**执行，所以 `when`/`retry`/`timeout`/`continueOnError` **照常生效**。这正是 `foreach` 能保持简短（约 200 行）的原因。

`foreach` 的 body 里 `.item` / `.index` 生效，body step 的 id 按 `<step>[<i>].<id>` 命名空间化，避免跨项结果碰撞。

## 8. 自描述（供 Agent 构图）

```
ListTypes()             → 有哪些积木
Describe(kind)          → 每块积木的参数 schema + Example + SubSteps
Schema()                → workflow 定义本身的 JSON Schema
Env.Catalog.ListTools() → 有哪些工具（name + inputSchema/outputSchema）
Parse(agentGenerated)   → 同一个库校验，错误回给 Agent 修正
```

**防漂移测试**（`TestDescribeAndExampleAgree`）：每个注册 kind 的 `Example` 必须能通过**它自己的** `Config` schema。漂移就测试红。

## 9. 与 pluginkit 的关系

| 维度 | pluginkit | workflowkit |
|---|---|---|
| 注册 | `init()` + kind + 构造函数 | **相同** |
| 构造函数形态 | `New()` / `New(cfg)` / `New(cfg, deps)` | `New()` / `New(cfg)`（**无 deps**） |
| 重复注册 | panic | **相同** |
| 自描述 | `Describe` / `ListKinds` / `Template` | `Describe` / `ListTypes` / `Schema` |
| **能力注入** | 构造期 `deps`（装配期实例图） | **运行期 `env` 参数** |
| config 严格性 | 核心统一 `DisallowUnknownFields` | **下放到节点**（因定义文件扁平） |

**为什么能力走运行期**：pluginkit 的 deps 是启动时建好、生命周期不变的实例图；而 workflowkit 是嵌入式库，宿主可能每次 Run 用不同能力（多租户、测试 mock）。走构造期会让 `init()` 注册时拿不到能力，并且多租户**共享一份能力**，与"无状态"冲突。

**为什么不依赖 pluginkit 本身**：那会引入 `yaml.v3`。workflowkit 的 NFR-1 是"只依赖标准库 + JSON Schema"，目前 `go list -deps` 的结果正是这样。

## 10. 测试布局

`workflowkit_test.go`（外部测试包 `workflowkit_test`）—— 从宿主的视角测，覆盖需求文档的验收项：

| 组 | 覆盖 |
|---|---|
| 加载期校验 | 13 类非法定义、隐式边成环、未知 kind 列出已注册类型、子步骤递归校验、inputs schema |
| 执行语义 | 串行序、`dependsOn: []` 并行（计时）、`concurrency` 上限、`when` 跳过、失败中止下一层、`continueOnError`、`retry` 次数、step 超时、取消 |
| 数据传递 | 大输出 spill 到文件、整数 >2^53 两跳、对象参数、`result` 渲染、`readJSON` 越权拒绝 |
| 节点类型 | model 的 `outputSchema` 三种失败、prompt 上限、agent、缺能力报错含 step id |
| foreach | 逐项执行、空数组、`onItemError` 两态、body 内 retry 生效 |
| 自定义类型 | 自定义 kind 跑通、**自动获得核心特性**（retry/continueOnError）、重复注册 panic |
| 自描述 | Example 与自身 schema 一致、内置 Example 组成的最小 workflow 过 `Schema()`、`Schema()` 拒绝坏定义 |
| 加载器 | `LoadDirs` 本地优先、坏文件不阻断、按 id 排序、`Dir` 正确 |

内部测试（需要白盒时）放在同包文件里；目前只有 `foreach` 的 id 命名空间化需要白盒观察，暂由外部测试间接覆盖。
